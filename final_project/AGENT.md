# Agent 與工具

## Gemini 建議生成（2026-11-23）

選擇 Gemini 時，先依資料與既有規則產生適合度、可引用的候選措施，再由 Gemini 根據本輪問題、已確認活動、族群、官方觀測／預報及可用天氣撰寫「建議做法」。模型須回傳結構化 actions 與候選依據編號；程式檢查來源、數字、活動依據、時段、重複及與判定的衝突。這些檢查不是完整語意或醫療審查。呼叫失敗或檢核未通過時保留規則建議，明確回傳 recommendationProvider 與 recommendationWarning。

介面在建議區標示「Gemini 生成」或「規則建議」，可直接點選「使用 Gemini 產生建議」並保存模型選擇；規則模式不將問題送至 Gemini。預設模型改為實測可用的 gemini-3.1-flash-lite，仍可由 GEMINI_MODEL 覆寫。

已解析出縣市時，Gemini 直接用於建議生成，省去重複的模型意圖解析；未能確定縣市時才另外嘗試模型解析。限制輸出長度與思考層級，避免簡單查詢連續等待兩次模型呼叫。

## 活動依據與建議（2026-11-22.5）

Profile.activitySource 記錄 explicit（本輪明確提到）、inherited（沿用先前明確活動）或 unspecified（未指定）。模型不能自行寫入活動、強度與時長；舊 Profile 沒有活動來源時不視為已確認的運動計畫。僅換地點或族群的追問可沿用已確認活動；一般空品、天氣、口罩問題未提活動時採一般外出參考。否認活動會清除舊活動，明確改做其他活動則採新活動。

未指定活動時不產生跑步／慢跑計畫，介面不顯示假設的運動強度與時長。沿用活動時在本次條件中標示來源。驗證器會拒絕缺乏使用者活動依據的跑步建議；建議不再預設存在「原定跑步計畫」。

官方空品預報也使用相同的活動／族群／污染物／天氣建議選擇流程，採用預報 AQI 與主要污染物，標明區域預報範圍；不以固定三句覆蓋使用者詢問的內容。

## 官方空品預報（2026-11-22）

未來問題會查詢環境部 AQF_P_01，依臺灣日期、縣市所屬空品區及最新發布批次，取全日或對應上午／下午預報。預報資料經日期、發布時間與 AQI 範圍檢核；缺少資料時不以目前觀測代替。展示模式不產生假的明日預報。

有對應預報時可依官方等級與既有族群規則提供附帶不確定性說明的行程規劃參考；全日預報不能冒充晚上等未涵蓋時段。仍不推薦精確最佳出門時刻。即時測站失敗不阻擋獨立的預報查詢，回答中的預報 AQI 也須通過證據檢核。明日天氣只保留與臺灣明日日期重疊的預報區間，直接顯示於主要回答。

## 本輪訊息檢核

2026-11-22.4：前端不再用已編譯的舊規則攔截訊息，所有本輪問題送至後端，在資料查詢與模型呼叫前統一檢核。地點、出行及評估用語以可換序詞元辨識，包含「那適合去彰化嗎」「那去彰化適合嗎」「彰化適合去嗎」。無效訊息仍回傳 clarification 並保留 Profile；舊分頁載入新版前端後，後續後端規則更新不會再被前端舊規則擋住。HTML 設為 no-store，API 回覆包含意圖規則版本供驗證。

換地點的追問以「出行／查詢前綴＋地點＋評估後綴」辨識，涵蓋「那去彰化呢」「改去彰化的話呢」「我想換到彰化可以嗎」等句型，不因缺少「空品」關鍵字而攔截。僅接受可辨識的地點與出行／評估語意；餐廳、股票等無關內容和亂碼仍不直接觸發空品評估。回歸測試涵蓋各縣市的同類句型，以及連續重問同一句。

縣內城市名稱（如彰化市、屏東市、宜蘭市）由共用地名解析對應至所屬縣；「那彰化市適合嗎」可沿用對話條件，回覆明確以彰化縣資料為依據。正式獨立縣市（新竹市／縣、嘉義市／縣）不可混用。無效訊息後的有效地點追問仍須正常處理。

2026-11-22 修正：前後端共用 `shared/message-intent.mjs`，辨識「嘉義市的狀況」「台中的狀況」「接著看台中」等地名查詢。已有縣市上下文時，僅切換地點的追問保留時間、時段、活動與族群；明確的新問題或時間修正仍依既有規則更新。地名夾雜餐廳、股票或亂碼仍不視為有效空品查詢。

進入模型解析或資料工具前，先由 `server/message-intent.mjs` 檢查本輪是否含可辨識的空品、戶外活動、相關族群問題，或明確的地點／時間／時長補充。舊 Profile 或「那／如果／呢」字樣本身不構成有效意圖。亂碼與無關問題回傳 `status: clarification`、`clarificationReason: unrecognized_message`，不查詢資料、不呼叫模型、不輸出舊 AQI 或評估卡，也不改寫原 Profile。接著正常追問仍可延續原條件。此為受控規則檢核，未涵蓋所有自然語言表達。

## 情境建議選擇（2026-11-07）

server/recommendations.mjs 取代原本固定的「準則／活動調整／症狀提醒」三句。依問題是否詢問口罩、替代活動、天氣、時段，以及活動類型、族群、強度、時長、指標污染物、資料完整性選出候選做法，再排序與去重，每次最多三點。沒有未來空品證據時只提供限制與重新查詢建議，不產生虛構最佳時段。

新增 generate_recommendations 工具軌跡；details.recommendations 保存 id、文字、觸發原因、來源與 kind。官方準則摘要、活動情境整理及資料限制分開標示。後端活動適合度仍由原健康規則引擎決定，建議選擇不會覆寫判定；不採用隨機換句話。來源包含環境部、衛福部、國健署、WHO 與 CDC／NIOSH 防護資訊，詳細分析可逐項查閱。

## 對話條件更新（2026-11-07 修正）

完整新問題沒有指定時間時，預設查現在，不沿用前一題的明天／早晚。明確改成今天／現在／目前時，清除舊 timeDetail；同一句多次修正以最後指定為準。「那如果我是氣喘患者呢？」等延續追問則保留前題的時地與活動，只更新族群。明早／明晚正規化為明天的早上／晚上。模型解析不能把舊時間覆寫回新問題，切換活動時重新推定強度。

顧問新增「重新對話」，保留所選縣市，清除其他個人條件、畫面紀錄與語音狀態；同時取消舊請求，晚到的回覆不會重新寫入新對話。此按鈕不刪除 SQLite 研究紀錄。

## 決策例

「現在適合慢跑嗎？」呼叫測站、分析、準則與驗證；不查天氣或歷史。

「明天什麼時候散步？」再加入天氣、歷史與時段資料充分性檢查。即使已有歷史曲線，也回覆無法可靠挑出未來最佳時間。

Gemini／Ollama 負責意圖與是否需要天氣／歷史的需求判讀，輸出欄位需白名單驗證。工具由後端執行。Gemini 另可根據已取得的證據撰寫建議，適合度與資料判定仍由規則決定；Ollama 目前僅用於意圖解析。建議實際來源由 recommendationProvider 標示，不以意圖解析成功冒充 Gemini 已生成建議。

對話上下文由前端 Profile 維持。可記住地區、族群、活動、強度、時長、時段；沒有實作完整聊天歷史送入模型，代名詞與複雜跨輪問題仍有解析限制。

## 安全與驗證邊界

只允許既定端點與工具，不允許模型執行程式碼或任意 URL。數字驗證只檢核本系統受控回答及結構化事實，不等同完整語義、醫療或文獻正確性審核。研究人工評分仍有必要。
